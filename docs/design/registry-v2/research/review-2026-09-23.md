# Adversarial review of the v2 design draft (2026-09-23)

> Point-in-time research note, 2026-09-23. A Claude agent reviewed the first
> complete draft of [../design.md](../design.md) against the six v1 research
> notes in this directory and the source at commit `f96fb751`, looking for
> soundness holes, schema inconsistencies, contradictions with verified v1
> behaviour, missing scenarios, ambiguities and misleading names. The
> findings are reproduced as delivered; **the design that shipped in the same
> PR is the post-review version**, and every finding's disposition
> (accepted, or rejected with a reason) is recorded in
> [../decisions.md](../decisions.md). Names used here are the draft's:
> `plan_task` became `plan_member`, `requires_registered_at` became
> `expanded_at`, and the execution outcome `superseded` became `taken_over`.

Findings are ranked by severity. Each gives a failing sequence or a concrete
ambiguity, and ends with a one-sentence fix.

## A. Soundness

**1. `exec_config` is allowed to affect output, but completion is global.**

- The draft said env vars never affect output or structure "except through
  the deployment or `exec_config`, which are part of the scope by
  construction." The scope keys structure only; `task_id` and the claim are
  global.
- Failing sequence: build A runs with `exec_config={MODEL=v1}` and completes
  T. Build B runs with `{MODEL=v2}`, sees T COMPLETED, and reuses v1 output
  as if it were v2. Scenario S8 ("the other reuses the result") is sound
  only under the opposite contract.
- Fix: state that `exec_config` may change structure and execution, never
  output, and say so in the user docs next to `significant`.

**2. A plan stops being closed under dependencies once an instance is shared
across plans. Deadlock.**

- Instances are unique per `(scope, instance_hash)`, so scope-mates share
  them. Edges and the closure flag are properties of the instance, but
  membership belongs to the plan.
- Dynamic case: plans PA and PB, same scope, both hold instance i of T. PA's
  worker yields C: C becomes a member of PA and the edge i→C is written. PB
  gets i→C as a gate, but C is not a member of PB. Build A is cancelled,
  excludes C, or is superseded by rollover. PB has i gated on C; C is in no
  active plan, and i's flag is set, so there is no discovery job either. PB
  stalls forever.
- Static case: PB registers i pruned-complete (flag NULL). T is invalidated,
  and PA expands i: the flag is set, with edges to u, which is admitted to
  PA only. PB now sees the flag set, runs no discovery job, and stays gated
  on a u it does not hold.
- The server also never checked that a declared upstream is a _member_ of
  the plan, only that the instance exists in the scope. This is exactly why
  v1 re-runs closure at stall. The draft's claim that closure at stall is
  "unnecessary as a separate mechanism" was wrong. Admitting u into PB can
  also fail with a PK conflict if PB already holds a different u', so
  `instance_conflict` can surface mid-build.
- Fix: make the frontier admit, in the same transaction, every upstream
  instance of a member's edges that the plan lacks (closure over edges), and
  report a conflict found there as a build failure that names both members.

**3. A lapsed claim is invisible to the runnable rule. Deadlock after any
worker death.**

- `ACTIONABLE` omitted RUNNING, and `running(m)` required a live claim. A
  worker OOM-killed never reports; `claim_expires_at` passes; T is RUNNING
  with an expired claim, so it is neither runnable nor running, and nothing
  takes it over. v1 includes RUNNING in actionable precisely so an expired
  claim is taken over.
- Fix: `ACTIONABLE` must include `RUNNING AND claim_expires_at <= now()`.

**4. Output location is per instance, while completion is per `task_id`.**

- `output_uri` lives on `task`. A `target()` that reads a non-significant
  field gives two instances two paths for one completion. i1 completes T at
  path A; i2's downstream sees T COMPLETED, reads path B, and finds nothing
  or stale data.
- Fix: compute `output_uri` per instance at registration and 409 when it
  differs from `task.output_uri`, i.e. make "the target is a function of
  significant fields" a checked rule.

**5. Invalidation landed after the chunk, so downstreams could run first.**

- The draft registered the instance and then called `invalidate` as a
  separate request, while the frontier may act on an unsealed plan. Chunk k
  registers i (COMPLETED in the registry, target missing); chunk k+1
  registers downstream D with the edge D→i; every upstream of D reads
  COMPLETED, so D is runnable; a tick claims D, which reads a missing input;
  the invalidate arrives afterwards.
- Fix: carry the observation on the chunk item and apply it in the same
  transaction as the edge inserts.

**6. Roots were registered last, and `sealed_at` was unverified. A crash was
unrecoverable, and completion could be premature.**

- Post-order puts roots in the final chunk, and `build.root_task_ids` stores
  completion ids only. If the bootstrap dies before the root chunk lands, no
  tick can resume: no root bodies to rehydrate, no discovery job, nothing
  runnable. Conversely, a driver whose chunk failed on a path that tolerates
  outages could still call `/seal`; missing members gate nothing, so the
  build completes with work never registered.
- Fix: register the root instances first, unexpanded (they become discovery
  jobs, so any tick can finish the static phase), and have `/seal` verify
  that every root is a member and that every member's upstreams are members.

**7. An excluded member still gated its downstreams, and an excluded root let
the build complete without its request.**

- Excluding X leaves X's downstream D neither runnable nor excluded, so the
  build never completes and never fails. Excluding a root marks the build
  COMPLETED with its requested output absent.
- Fix: exclusion cascades to the downstream closure within the plan, like
  skip-blocked, and excluding a root fails the build.

**8. The resident engine did not fit "one claim → one execution → authority by
`execution_id`".**

- v1 claims only when `supports_detached` (`_concurrent.py:687-699`); thread-
  and process-pool executions are unclaimed and rely on the deprecated global
  lock. Under the draft's rule an unclaimed local run's `/complete` names no
  current execution and is refused, so a local `sd.build()` cannot complete
  anything. If instead every local run claims with a TTL, a long run lapses
  (no heartbeats) and another build takes it over: two live executions.
- Separately, the resident engine keeps the generator in-process. `/yield`
  with `suspend: true` releases the claim while that generator is alive; a
  reactive build then claims the SUSPENDED task and runs it from scratch
  while the resident engine resumes it.
- Fix: specify resident semantics explicitly — a resident claim held with a
  NULL expiry until the terminal report, `suspend: false` for resident yields,
  and say what replaces the global lock.

**9. Rollover could move backwards.**

- The "current deployment is mine" check ran at step 1, not at seal. D2 is
  deployed; tick₂ starts registering P2. D3 is deployed; tick₃ creates P3,
  seals it, and supersedes P1. tick₂ seals P2, which supersedes P3. The build
  is now on older code.
- Fix: `/seal` re-checks, in its own transaction, that `plan.deployment_id`
  is the app's current deployment, and refuses otherwise.

**10. `execution.ended_at` was written when the claim moved, not when the
execution ended.**

- Nobody observes a lapse: the server has no timer, and the watchdog only
  spawns ticks, so `lapsed` could only be written lazily at the next
  takeover. A takeover that writes `ended_at` on E1 while E1's container
  still runs removes E1 from the orphan definition (`ended_at IS NULL`) and
  from `builds stop --not-in-current-plan`. This contradicts "an execution
  ref is not a claim".
- Fix: split the columns — `claim_released_at` + `claim_outcome` written by
  the server; `ended_at` written only by the execution's own report or a
  stop.

**11. A retried or late POST was not a no-op (STA-54).**

- E reports `/fail`; the operator retries T (now PENDING, no claim); a
  delayed duplicate of E's `/fail` arrives; T holds no claim and E is the
  "latest ended" execution, so the duplicate is applied and T is FAILED
  again. A retried `/yield` or `/complete` re-applies the same way and
  appends duplicate events.
- A retried claiming start whose first delivery was granted gets 409
  `plan_superseded` if a seal landed in between; the tick thinks it lost and
  the task stalls for the TTL (the STA-94 shape).
- A retried `invalidate` that arrives after T has re-completed un-completes
  a fresh output.
- A chunk retry is a no-op only if the event insert is gated on the
  membership insert's `RETURNING`, which the draft did not say.
- Fix: apply at most one terminal report per `execution_id`; check "same
  execution already holds the claim" before `plan_superseded`; give
  `invalidate` an expected-state precondition; gate event writes on actual
  inserts.

**12. Lock ordering (STA-48/51).**

- Claim arbitration takes `FOR UPDATE` on `task`, and in Postgres that
  conflicts with the `FOR KEY SHARE` that every `task_instance`,
  `plan_task`, `event` and `execution` insert takes via its FK to `task`. So
  "the registration transaction takes no FOR UPDATE" did not remove the
  contention.
- Two chunks inserting the same brand-new `task_id`s or
  `(scope, instance_hash)`es in different orders deadlock on unique-index
  waits.
- If build status is "derived in the same transaction as the event", a
  TASK_COMPLETED must lock every build whose active plan holds T — a
  task→build order, while `_flag_builds` needed `SKIP LOCKED` to avoid
  exactly that inversion.
- Fix: arbitrate with `FOR NO KEY UPDATE`; insert chunk rows sorted by
  `(task_id, instance_hash)`; keep build completion client-driven, with
  `/complete` checked against `plan_complete` rather than derived in the
  task transaction.

## B. Schema consistency

**13. "Exactly one active plan" cannot hold while a replacement plan is being
registered.**

- A newly created plan has `superseded_at IS NULL`, so it violates
  `UNIQUE (build_id) WHERE superseded_at IS NULL` until seal, yet the first
  plan must be active while unsealed.
- Fix: add `activated_at`; the first plan activates on create, a replacement
  on seal; the partial unique becomes
  `WHERE activated_at IS NOT NULL AND superseded_at IS NULL`.

**14. Deleting a build left a claim nobody could release.**

- `claim_plan_id` SET NULL, executions cascade, `task.execution_id` SET NULL.
  A still-running worker's `/complete` names E ≠ NULL, so it is refused, into
  an execution row that no longer exists. With `claim_expires_at IS NULL`
  the task is RUNNING permanently for every other plan. The cascade to
  events also deletes global fold sources, a v1 bug repeated.
- Fix: refuse to delete a build that still holds live claims (or release
  them in the delete transaction), and make `event.build_id` SET NULL.

**15. `event.build_id NOT NULL` conflicted with environment-level writes.**

- Operator `invalidate` and concurrency-limit `evict` (which writes
  TASK_FAILED) have no build. `plan_id` was undefined for build-level
  events. `report_applied` lived on both `execution` and `event`; one
  execution can have one applied and one refused report.
- Fix: nullable `build_id` with a CHECK tying it to the event type;
  `report_applied` on `event` only.

**16. `plan_task` counters diverged from the global claim.**

- `attempt_count` per `(plan, task)` while executions are global: T
  crash-loops under PA's executions, PB's counter never moves, so PB keeps
  resetting and re-running T. Every rollover or new `exec_config` restarts
  the counters at 0 — STA-44's "retry budget silently grew". The counters
  also duplicate what the ledger holds.
- Fix: derive the budget from `execution` rows over the build's plans, and
  drop the counters.

**17. Limit keys were per `task`, but limit-key selection is per instance.**

- A selector reading a non-significant field (a GPU type) gives two
  instances different keys.
- Fix: write the keys at claim time from the claiming execution's instance,
  and replace them on every claim.

**18. Consistency the constraints did not enforce.**

- `plan_task.task_pk` must equal `task_instance.task_pk`: use a composite FK
  `(instance_id, task_pk)`.
- Edge scope equality relied on "read in the same statement": use composite
  FKs including the scope columns.
- `execution` was called append-only yet has `ended_at`/`outcome` updated.
- `task.executor*` was copied from `execution`: one fact, two sources.
- ON DELETE for `deployment` was unstated; STA-68 retention will delete
  deployments.
- The creation quota counted `task` rows, so varying a non-significant field
  creates unbounded instances.

## C. Contradictions with v1 lessons

**19. A re-trigger with a different root body silently reused the sealed plan
(STA-43 reborn).**

- The plan is unique on `(build, scope)`, and "an existing sealed plan is
  reused without discovery". Re-triggering the same root `task_id` with a
  changed non-significant field, under the same scope, keeps the old body.
  A conflicting body on an instance insert (`DO NOTHING`) is also silently
  dropped; "`instance_hash ↔ body` 1:1" was a client promise the server never
  checked.
- Fix: a mismatch of root instances is 409, and an instance insert conflict
  compares bodies and returns 409.

**20. Resuming a sealed plan without discovery dropped two v1 behaviours.**

- v1 resume re-runs discovery with `retry_failed`. Reuse leaves
  FAILED/CANCELLED members as they are, so the resumed build fails again
  immediately; it also never checks targets, so invalidation never fires on
  resume.
- Fix: resume performs the member resets and a target check even when it
  reuses the plan.

**21. Yields were attributed to the plan's scope, not to the worker's code.**

- A local `sd.build()` with a `ModalTaskExecutor` runs under a local-kind
  deployment while the workers run code D; `/yield` records children computed
  by D's code as instances and edges of the local scope. And
  `reactive_discovery="local"` plans under a local deployment, so every such
  build is discovered twice (the first tick must roll over) and fails on a
  dirty tree whose root ids differ.
- Fix: `/yield` refuses unless the worker's deployment equals the plan's, and
  drivers whose tasks run on an app plan under that app's deployment.

**22. Removing `compat_default` brought back the version-bump cascade that
#340 was rejected for.**

- Adding any significant field would change every downstream id. Removal is
  orthogonal to the two-hash change.
- Fix: keep `compat_default` on significant fields.

**23. `exit-early` releasing claims was a policy change.**

- The v1 rule covers cancel and fail only. A resident exit-early would
  release the claims of in-flight in-process tasks, and a reactive build
  then duplicates them.
- Fix: release claims on complete, fail and cancel; state what exit-early
  does separately.

**24. S2 said a conflict is caught "synchronously at the trigger". True only
for static conflicts.**

- A dynamic child conflicting with a static member is found at `/yield`; it
  then fails the parent, the retry budget re-runs it, and it fails again
  deterministically.
- Fix: `instance_conflict` at yield is non-retryable and fails the member
  with both paths named.

## D. Missing scenarios

**25.** The checklist should add: lapsed-claim takeover (3); a cross-plan
shared instance with a dynamic yield, then the yielding build cancelled (2);
the `shared_structure_scope` regression — two instances of one completion in
one scope do not share dynamic edges, so the pre-yield section re-runs (the
property v1 tests); a resident `sd.build()` with thread and process pools;
a local driver with Modal workers (21); `exec_config` setting a `STARDAG_*`
key or a selector key (27); a yielded child that is COMPLETED but whose
target is missing; a yielded child RUNNING in another build; `invalidate`
racing a claiming start, and a re-completion racing a retried invalidate;
`/seal` while a timed-out chunk retry is still in flight; two ticks under D2
and D3 (9); an excluded member with downstreams, and an excluded root; a
discovery job whose class is not importable in the tick (fail the member
after one attempt rather than retrying every tick forever); a crash before
the root chunk (6); a duplicate delayed `/fail` after an operator retry (11);
a deleted build holding a claim (14); deploy recording lag or failure (every
new-code tick exits `superseded`, permanently if the record failed); two
near-simultaneous deploys whose records arrive out of order.

## E. Ambiguities an implementer would have to guess

**26. Request shapes.** Are `declared_upstreams` referenced by `task_id` or by
`instance_hash`? (`task_id` is ambiguous when a scope holds several instances
of one completion.) In `/yield`, how are the yielded children marked apart
from their closure items? Does `/complete` still exist, given build status is
"derived and stored"? Does the frontier take a build or a plan, and does it
return `plan_id`? How does a worker receive its plan id?

**27. `exec_config` mechanics.** Precedence `exec_config > selector >
deployment` lets a user override `STARDAG_PLAN_ID`, `STARDAG_DEPLOYMENT_ID`,
`STARDAG_EXECUTION_ID`, the API key or the registry URL. `os.environ` is
process-global: two concurrent `sd.build()` calls in one process clash, and
setting it without restoring leaks into the caller. Warm Modal containers and
the tick import modules before applying the build's `exec_config`, so values
read at import time are stale. Also undefined: how `exec_config` reaches
thread-pool tasks and process pools reused across builds; the canonical hash
of `{}`; who inserts the "always present" empty row. Fix: reserve
`STARDAG_*`/`MODAL_*`, apply only in a scoped `temp_env_vars`, and state
"read at run time only".

**28. Hashing and rehydration.** Does a nested task enter `instance_hash` as
its `task_id` or as its `instance_hash`? (With `task_id`, two bodies share an
`instance_hash` and first-write-wins returns at the nested level.) Are
defaults included? What does "computed by the SDK under that scope" mean,
when scope is not an input to the hash? Is rehydration of an old body under
new code strict or lenient? Which of `STARDAG_DEPLOYMENT_ID` and
`STARDAG_CODE_ID` wins when both are set locally?

**29. What "self-consistent chunk" obliges the server to check.** Upstream
instance exists in scope? Upstream is a member of this plan? Flag set exactly
when `declared_upstreams` is non-null? Member count or roots at seal? S12
relied on a timing argument, not a constraint; the chunk item should carry
the driver's completion observation and the server should apply it in the
same transaction.

## F. Naming

**30.** `exec_config` reads as execution-only config, yet it is scope and
structure (suggest `build_env`). `requires_registered_at` reads as "a
dependency must be registered at"; it is the closure flag (suggest
`expanded_at`). "superseded" carried three meanings: `plan.superseded_at`,
the `execution.outcome` value, and the tick exit. `task` / `task_id` /
`task_pk` / `plan_task` put three identifiers and a join table under one
word, while the Python `Task` object is an _instance_ (suggest
`plan_member`, and `completion_id` in the API only). `admitted_by = closure`
named a mechanism the draft said it deleted; finding 2 says it must stay.
